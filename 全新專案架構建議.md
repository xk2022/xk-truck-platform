## 一、整體架構決策

### 1.1 架構模式選擇

#### ✅ 推薦：模組化單體（Modular Monolith）+ 微服務準備

**理由：**
- ✅ **開發效率高**：初期開發與調試容易
- ✅ **部署簡單**：單一應用，無需複雜的服務治理
- ✅ **效能優良**：無網路延遲，事務處理簡單
- ✅ **可擴展性**：模組邊界清晰，未來可拆分為微服務
- ✅ **成本效益**：初期不需要複雜的基礎設施

**何時考慮微服務：**
- 團隊規模 > 20 人
- 業務模組需要獨立擴展（例如：訂單模組需要更高併發）
- 技術棧需要多樣化（例如：AI 模組需要 Python）

## 四、分層架構設計

### 4.1 API Layer（Presentation Layer）

**職責：**
- HTTP 請求/回應處理
- 參數驗證（`@Valid`）
- DTO 轉換
- 權限檢查（`@PreAuthorize`）
- 統一例外處理

**範例：**

```java
@RestController
@RequestMapping("/api/v1/fms/vehicles")
@RequiredArgsConstructor
@Tag(name = "FMS - Vehicles", description = "車輛管理 API")
public class VehicleController {

    private final CreateVehicleUseCase createVehicleUseCase;
    private final VehicleQueryUseCase vehicleQueryUseCase;
    private final VehicleApiMapper mapper;

    @PostMapping
    @Operation(summary = "建立車輛")
    @PreAuthorize("hasAuthority('FMS_VEHICLE_CREATE')")
    public ApiResult<VehicleResp> create(@Valid @RequestBody VehicleCreateReq req) {
        CreateVehicleCommand cmd = mapper.toCommand(req);
        Vehicle vehicle = createVehicleUseCase.execute(cmd);
        return ApiResult.success(mapper.toResponse(vehicle));
    }

    @GetMapping
    @Operation(summary = "查詢車輛列表")
    @PreAuthorize("hasAuthority('FMS_VEHICLE_READ')")
    public ApiResult<PageResult<VehicleResp>> list(
            @Valid VehicleQueryReq query,
            Pageable pageable) {
        VehicleQuery queryModel = mapper.toQuery(query);
        Page<Vehicle> vehicles = vehicleQueryUseCase.execute(queryModel, pageable);
        return ApiResult.success(mapper.toPageResponse(vehicles));
    }
}
```

### 4.2 Application Layer

**職責：**
- 協調 Domain 層完成業務用例
- 事務管理（`@Transactional`）
- 領域事件發布
- 跨 Aggregate 協調

**範例：**

```java
@Service
@RequiredArgsConstructor
@Transactional
public class CreateVehicleUseCase implements CreateVehicleUseCaseInterface {

    private final VehicleRepository vehicleRepository;
    private final DomainEventPublisher eventPublisher;
    private final VehicleFactory vehicleFactory;

    @Override
    public Vehicle execute(CreateVehicleCommand cmd) {
        // 1. 檢查唯一性
        vehicleRepository.findByPlateNo(cmd.getPlateNo())
                .ifPresent(v -> {
                    throw new VehiclePlateNoExistsException(cmd.getPlateNo());
                });

        // 2. 使用 Factory 建立 Aggregate
        Vehicle vehicle = vehicleFactory.create(
                cmd.getPlateNo(),
                cmd.getType(),
                cmd.getBrand(),
                cmd.getModel()
        );

        // 3. 儲存
        Vehicle saved = vehicleRepository.save(vehicle);

        // 4. 發布領域事件
        eventPublisher.publish(new VehicleCreatedEvent(saved.getId(), saved.getPlateNo()));

        return saved;
    }
}
```

### 4.3 Domain Layer

**職責：**
- 業務邏輯核心
- 不依賴任何框架
- Aggregate 不變式維護
- 領域事件定義

**範例：**

```java
/**
 * Aggregate Root: Vehicle
 * 負責維護車輛的業務不變式
 */
public class Vehicle {

    private VehicleId id;
    private PlateNo plateNo;  // Value Object
    private VehicleType type;
    private VehicleStatus status;
    private Brand brand;
    private Model model;
    private Capacity capacity;
    private DriverId currentDriverId;

    // Factory Method
    public static Vehicle create(
            PlateNo plateNo,
            VehicleType type,
            Brand brand,
            Model model,
            Capacity capacity) {
        return new Vehicle(
                VehicleId.generate(),
                plateNo,
                type,
                VehicleStatus.AVAILABLE,  // 新建預設狀態
                brand,
                model,
                capacity,
                null
        );
    }

    // Domain Method
    public void assignDriver(DriverId driverId) {
        if (this.status != VehicleStatus.AVAILABLE) {
            throw new VehicleNotAvailableException(this.id, this.status);
        }
        if (this.currentDriverId != null) {
            throw new VehicleAlreadyAssignedException(this.id, this.currentDriverId);
        }
        
        this.currentDriverId = driverId;
        this.status = VehicleStatus.BUSY;
        
        // 領域事件
        DomainEventPublisher.instance().publish(
                new VehicleAssignedEvent(this.id, driverId)
        );
    }

    public void releaseDriver() {
        if (this.status != VehicleStatus.BUSY) {
            throw new IllegalStateException("Vehicle is not busy");
        }
        
        this.currentDriverId = null;
        this.status = VehicleStatus.AVAILABLE;
    }

    // Getters (Immutable)
    // ...
}
```

### 4.4 Infrastructure Layer

**職責：**
- Repository 實作
- 外部服務適配器
- 技術細節實作（快取、訊息佇列等）

**範例：**

```java
@Repository
@RequiredArgsConstructor
public class VehicleRepositoryAdapter implements VehicleRepository {

    private final VehicleJpaRepository jpaRepository;
    private final VehicleEntityMapper mapper;

    @Override
    public Optional<Vehicle> findById(VehicleId id) {
        return jpaRepository.findById(id.getValue())
                .map(mapper::toDomain);
    }

    @Override
    public Optional<Vehicle> findByPlateNo(PlateNo plateNo) {
        return jpaRepository.findByPlateNo(plateNo.getValue())
                .map(mapper::toDomain);
    }

    @Override
    public Vehicle save(Vehicle vehicle) {
        VehicleEntity entity = mapper.toEntity(vehicle);
        VehicleEntity saved = jpaRepository.save(entity);
        return mapper.toDomain(saved);
    }

    @Override
    public Page<Vehicle> findAll(VehicleSpecification spec, Pageable pageable) {
        Specification<VehicleEntity> jpaSpec = mapper.toJpaSpecification(spec);
        return jpaRepository.findAll(jpaSpec, pageable)
                .map(mapper::toDomain);
    }
}
```

## 五、OrderCore 與 TOM 的關係設計

### 5.1 為什麼要分離？

#### ⚠️ 合併的風險

如果將 OrderCore 與 TOM 合併為單一模組，會有以下風險：

1. **違反單一職責原則**
   - 一個模組同時負責「命運層」（OrderCore）和「流程層」（TOM）
   - 職責不清，難以維護

2. **未來擴展困難**
   - 如果未來需要新增其他 Domain（例如：COM 電商訂單、SOM 銷售訂單）
   - 這些 Domain 都需要 OrderCore，但不需要 TOM 的運輸邏輯
   - 如果合併，會造成不必要的依賴

3. **微服務拆分困難**
   - 如果未來需要拆分微服務
   - OrderCore 應該作為獨立的服務（被多個服務共用）
   - TOM 可以作為獨立的服務
   - 如果合併，拆分時會遇到問題

4. **測試複雜度增加**
   - 合併後，測試 OrderCore 時會牽扯到 TOM 的邏輯
   - 測試 TOM 時也需要考慮 OrderCore 的邏輯
   - 分離後，可以獨立測試

#### ✅ 分離的優點

1. **職責清晰**
   - OrderCore：只負責訂單的「命運層」狀態（OPEN / CANCELLED / CLOSED）
   - TOM：只負責運輸訂單的「流程層」狀態（NEW → ACCEPTED → ASSIGNED）

2. **可重用性**
   - OrderCore 可以被多個 Domain 共用：
     - TOM（運輸訂單）
     - COM（電商訂單，未來）
     - SOM（銷售訂單，未來）
     - FIN（財務訂單，未來）

3. **獨立演進**
   - OrderCore 和 TOM 可以獨立開發、測試、部署
   - 修改 OrderCore 不會影響 TOM
   - 修改 TOM 不會影響 OrderCore

4. **清晰的依賴關係**
   - TOM 依賴 OrderCore（單向依賴）
   - OrderCore 不依賴任何業務 Domain

#### 5.2.2 建立流程協作

**建立運輸訂單的流程：**

```java
@Service
@Transactional
@RequiredArgsConstructor
public class CreateTomOrderUseCase {

    private final CreateOrderCoreUseCase createOrderCoreUseCase;  // OrderCore 的 UseCase
    private final TomOrderRepository tomOrderRepository;

    public TomOrder execute(CreateTomOrderCommand cmd) {
        // 1. 先建立 OrderCore（命運層）
        CreateOrderCoreCommand coreCmd = CreateOrderCoreCommand.builder()
                .orderNo(generateOrderNo())  // 產生訂單編號
                .build();
        
        OrderCore orderCore = createOrderCoreUseCase.execute(coreCmd);
        // orderCore.status = OPEN（預設）

        // 2. 再建立 TomOrder（流程層）
        TomOrder tomOrder = TomOrder.create(
                orderCore.getOrderUuid(),     // 共享主鍵
                orderCore.getOrderNo(),       // 同步訂單編號
                cmd.getOrderType(),
                cmd.getCustomerUuid(),
                cmd.getPickupAddress(),
                cmd.getDeliveryAddress(),
                // ... 其他 TOM 專屬欄位
        );
        // tomOrder.tomStatus = NEW（預設）

        // 3. 儲存 TomOrder
        return tomOrderRepository.save(tomOrder);

    }
```

#### 5.2.3 狀態協同管理

**取消訂單的流程：**

```java
@Service
@Transactional
@RequiredArgsConstructor
public class CancelTomOrderUseCase {

    private final CancelOrderCoreUseCase cancelOrderCoreUseCase;  // OrderCore 的 UseCase
    private final TomOrderRepository tomOrderRepository;

    public void execute(CancelTomOrderCommand cmd) {
        // 1. 載入 TomOrder
        TomOrder tomOrder = tomOrderRepository.findById(cmd.getOrderUuid())
                .orElseThrow(() -> new TomOrderNotFoundException(cmd.getOrderUuid()));

        // 2. 檢查 TOM 流程狀態（業務規則）
        tomOrder.ensureCanCancel();  // Domain Method：檢查是否可以取消

        // 3. 更新 OrderCore 狀態（命運層）
        CancelOrderCoreCommand coreCmd = CancelOrderCoreCommand.builder()
                .orderUuid(cmd.getOrderUuid())
                .reason(cmd.getReason())
                .build();
        
        cancelOrderCoreUseCase.execute(coreCmd);
        // OrderCore.status = CANCELLED

        // 注意：TomOrder.tomStatus 保持不變（作為歷史記錄）
        // 但後續所有 TOM 操作都會檢查 OrderCore.status
    }
}
```

**查詢時的協同：**

```java
@Service
@Transactional(readOnly = true)
@RequiredArgsConstructor
public class FindTomOrderUseCase {

    private final TomOrderRepository tomOrderRepository;
    private final OrderCoreRepository orderCoreRepository;  // OrderCore 的 Repository

    public TomOrderDetailResult execute(FindTomOrderQuery query) {
        // 1. 載入 TomOrder
        TomOrder tomOrder = tomOrderRepository.findById(query.getOrderUuid())
                .orElseThrow(() -> new TomOrderNotFoundException(query.getOrderUuid()));

        // 2. 載入 OrderCore（檢查命運層狀態）
        OrderCore orderCore = orderCoreRepository.findById(tomOrder.getOrderUuid())
                .orElseThrow(() -> new OrderCoreNotFoundException(tomOrder.getOrderUuid()));

        // 3. 檢查訂單是否仍有效
        if (orderCore.getStatus() == OrderCoreStatus.CANCELLED) {
            throw new OrderCancelledException(tomOrder.getOrderUuid());
        }

        // 4. 組裝結果
        return TomOrderDetailResult.builder()
                .orderUuid(tomOrder.getOrderUuid())
                .orderNo(tomOrder.getOrderNo())
                .coreStatus(orderCore.getStatus())      // OrderCore 狀態
                .tomStatus(tomOrder.getTomStatus())      // TOM 流程狀態
                // ... 其他欄位
                .build();
    }
}
```

## 六、領域驅動設計（DDD）

### 5.1 Aggregate 設計原則

#### ✅ 推薦的 Aggregate 邊界

| 模組 | Aggregate Root | 說明 |
|------|---------------|------|
| **OrderCore** | OrderCore | 訂單核心（命運層），跨 Domain 共用，獨立 Aggregate |
| **TOM** | TomOrder | 運輸訂單（流程層），依賴 OrderCore，獨立 Aggregate |
| **FMS** | Vehicle、Driver | 車輛與司機各自獨立 Aggregate |
| **UPMS** | User、Role、Permission | 各自獨立，透過關聯表維護關係 |

**OrderCore 與 TOM 分離的理由：**

1. **職責分離（Single Responsibility）**
   - OrderCore：只負責訂單高階生命週期（OPEN / CANCELLED / CLOSED）
   - TOM：只負責運輸訂單的業務流程（NEW → ACCEPTED → ASSIGNED）

2. **跨 Domain 共用**
   - OrderCore 可被多個 Domain 共用：
     - TOM（運輸訂單）
     - COM（電商訂單，未來可能）
     - SOM（銷售訂單，未來可能）
     - FIN（財務訂單，未來可能）

3. **未來擴展性**
   - 如果合併，未來新增其他 Domain 會造成耦合
   - 分離後，每個 Domain 可以獨立演進

4. **微服務拆分準備**
   - 如果未來拆分微服務，OrderCore 可以作為獨立的服務
   - TOM、COM 等可以作為各自的服務，都依賴 OrderCore

5. **資料一致性**
   - OrderCore 與 TOM 共享 `orderUuid` 主鍵
   - 透過相同主鍵維護一致性，而非直接合併

#### Aggregate 設計原則

1. **一個 Aggregate 一個 Repository**
2. **透過 ID 引用其他 Aggregate**（不直接持有物件）
3. **Aggregate 內部保持一致性**（不變式）
4. **跨 Aggregate 操作透過 Domain Events 協調**

**範例：**

```java
// ✅ 正確：透過 ID 引用
public class Order {
    private OrderId id;
    private CustomerId customerId;  // 引用 Customer Aggregate
    private VehicleId vehicleId;    // 引用 Vehicle Aggregate
    private DriverId driverId;      // 引用 Driver Aggregate
}

// ❌ 錯誤：直接持有其他 Aggregate
public class Order {
    private Customer customer;  // 不要這樣做
    private Vehicle vehicle;    // 不要這樣做
}
```

**用途：**
- 跨 Aggregate 協調
- 非同步處理觸發
- 審計日誌
- 整合其他系統

### 5.3 Value Objects

**使用 Value Objects 增強語意：**

```java
// ✅ 使用 Value Object 代替原始類型
public class PlateNo {
    private final String value;

    private PlateNo(String value) {
        if (value == null || !isValid(value)) {
            throw new IllegalArgumentException("Invalid plate number: " + value);
        }
        this.value = value.toUpperCase().trim();
    }

    public static PlateNo of(String value) {
        return new PlateNo(value);
    }

    private boolean isValid(String value) {
        // 驗證車牌格式（台灣車牌：ABC-1234）
        return value.matches("^[A-Z]{2,3}-\\d{4}$");
    }

    public String getValue() {
        return value;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof PlateNo)) return false;
        PlateNo plateNo = (PlateNo) o;
        return Objects.equals(value, plateNo.value);
    }

    @Override
    public int hashCode() {
        return Objects.hash(value);
    }
}
```

### 7.1 資料庫遷移（Flyway）

**遷移腳本結構：**

```
resources/db/migration/
├── V1__Initial_schema.sql
```

**最佳實踐：**

- ✅ 使用版本號（V1__, V2__）
- ✅ 提供回滾腳本（可選，使用 U1__, U2__）
- ✅ 避免在生產環境直接修改資料（使用遷移腳本）

### 7.2 索引策略

**必須建立索引：**
- 主鍵（自動）
- 外鍵
- 唯一約束欄位
- 常用查詢條件（WHERE、JOIN）
- 排序欄位（ORDER BY）

**範例：**

```sql
-- 車輛表索引
CREATE INDEX idx_fms_vehicle_plate_no ON fms_vehicle(plate_no);
CREATE INDEX idx_fms_vehicle_status ON fms_vehicle(status);

CREATE INDEX idx_order_customer_id ON t_order(customer_id);
```

### 7.3 資料庫設計原則

1. **使用 UUID 作為主鍵**（或使用 ULID，更適合分散式系統）
2. **軟刪除**：使用 `deleted_at` 欄位而非物理刪除
3. **審計欄位**：`created_at`、`updated_at`、`created_by`、`updated_by`
4. **版本控制**：使用 `version` 欄位實現樂觀鎖
5. **時區處理**：統一使用 UTC 儲存，應用層轉換
